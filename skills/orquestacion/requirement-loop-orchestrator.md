# Requirement Loop Orchestrator

El agente principal opera el CLI de persistencia y despacha a los agentes mediante la delegación nativa de Codex. El CLI usa Python 3.9+ y PyYAML. Los cinco perfiles están en `.codex/agents/`.

## Entrada y despacho

Para un requerimiento nuevo, `python scripts/nuevo_requerimiento.py US-001 "Título"` conserva la inicialización y selección legadas. `python scripts/ejecutar_requirement_loop.py init` activa el esquema gestionado para el requerimiento seleccionado. `--requirement MA-001`, antes del subcomando, permite gestionar un requerimiento explícito sin seleccionar otro en el manifiesto. El handoff global solo se proyecta para el requerimiento seleccionado. El inicializador reutiliza una especificación existente con su nombre original.

1. Ejecuta `python scripts/ejecutar_requirement_loop.py reserve`. Usa `--source RUTA` repetible para congelar insumos locales inmutables de una entrega. La especificación canónica se añade a Analysis si existe. El código o documentos que el rol necesita modificar son salidas y se adjuntan al devolver su entrega.
2. Envía al rol indicado la reserva completa, sus contratos, evidencia y rúbrica. El campo `kind` distingue una entrega de una evaluación subordinada. El CLI devuelve el cursor persistido. La creación e inspección de hilos se realizan en Codex.
3. Vincula el recibo nativo mediante `bind DISPATCH_ID ROLE SESSION_ID`. El organizador verifica que el recibo corresponda al agente que invocó y envía exclusivamente su respuesta mediante `submit SESSION_ID RESULT.json`. El vínculo es auditado por el organizador con la procedencia visible de la sesión. El CLI verifica el enlace registrado y el rol de la reserva. El CLI depende del acceso de escritura del organizador y de su comprobación de los recibos nativos.
4. Si el actor indicado es `organizer`, registra su evaluación independiente de Validation con `submit organizer RESULT.json`. El CLI verifica el veredicto emitido por la sesión de Validation antes de materializar el cierre.

Consulta `status` para leer el estado, las evaluaciones, los intentos, las reservas y el historial. Para comprobar el esquema de un requerimiento seleccionado, ejecuta `python scripts/validar_requirement_loop.py`.

## Resultados

El resultado JSON incluye `event_id` único y `dispatch_id` de la reserva. Una entrega añade `artifacts` y `outcome`: `ANALYSIS_READY`, `IMPLEMENTATION_READY`, `SECURITY_EVIDENCE_READY`, `TEST_EVIDENCE_READY` o la disposición admitida para el rol. Security adjunta `gate` con `pass`, `not_applicable` o `fail`. En el segundo caso, adjunta una referencia `exception` a su autorización. Para un hallazgo crítico o alto, usa `SECURITY_FINDINGS_REWORK` y `gate: fail`. La entrega final de Validation puede proponer `COMPLETED` con un objeto `gates` que contiene los booleanos `dod`, `traceability`, `invariants`, `no_known_flaky`, `critical_high_closed` y `severe_defects_closed`. Adjunta en `artifacts` las comprobaciones de dominio que sustentan el veredicto.

Una evaluación añade un objeto `evaluation`. Copia del despacho `requirement_id`, `task_id`, `dispatch_id`, `revision`, `attempt`, `rubric_id` y `rubric_version`. Añade `evaluation_id` único, `role` con el valor de `subject`, `reviewer` con el valor de `role` de la reserva y `criteria` con una entrada por cada ID congelado. Cada entrada contiene `criterion_id`, `passed` booleano estricto y `evidence` con `references` y `justification`. Cada falso incluye `action` y, cuando falta un artefacto, `evidence.expected_locator` más una referencia al registro de la comprobación fallida. Para una excepción, incluye `evidence.exception` con la autorización. El CLI calcula `score` y verifica cualquier suma declarada. Si el defecto está en otro insumo, adjunta `rework` en el resultado y ofrece evidencia del defecto en el criterio fallido.

Cada referencia usa `{"path":"ruta/relativa.md","locator":"L1-L3","sha256":"<sha256 del archivo completo>"}`. Usa `L1` para una sola línea. Guarda informes y registros reproducibles dentro del repositorio, con una ruta por intento para conservar evidencia histórica. Evita secretos en rutas, nombres de sesión, artefactos y justificaciones.

El organizador declara con `reserve --source RUTA` los insumos previos que deben permanecer fijos durante el despacho. En el primer despacho de Developer, el CLI fija el commit `HEAD` como línea base de Git del requerimiento y lo conserva en rework. Ejecuta desde la raíz del repositorio con un commit base disponible y el índice Git sin cambios staged frente a `HEAD`. Un índice con cambios bloquea reservas, inventario y cierre. Toda entrega `IMPLEMENTATION_READY` declara `product_sources` con las rutas relativas del diff. El CLI compara la lista exacta con los cambios del worktree frente a la base y los archivos untracked que Git no ignora. Registra y revalida el modo Git de cada archivo. En Windows usa el modo del índice limpio para archivos rastreados y `100644` para archivos nuevos. Un rename cuenta ambas rutas y una baja se registra como ausencia. Solo admite una lista vacía cuando el inventario calculado está vacío.

Guarda resultados JSON en `docs/implementacion/requerimientos/<ID>/results/` y evidencia específica de ejecución en `docs/implementacion/requerimientos/<ID>/evidence/`. Estas dos carpetas de ejecución, el estado del requerimiento, el manifiesto, el handoff y los locks quedan fuera del inventario. Los despachos posteriores heredan las huellas y ausencias verificadas. El estado compara también el conjunto de cambios respecto de la línea base para detectar rutas añadidas después de la entrega.

`not_applicable` requiere `security.required: false` en el estado inicial y vigente, y `quality_gates.security_review_required: false` en el manifiesto. La entrada `quality_gates.security_exceptions.<ID>` incluye `authorization` con la referencia adjunta completa y `mode: permanent` o `mode: revision`. El segundo modo exige `revision` igual a la revisión exacta de la reserva de Security. Si cambia la autorización o se activa la exigencia de revisión, se reabre Security.

Usa archivos JSON regulares dentro del repositorio de hasta 256 KiB y YAML de hasta 16 MiB. Cada resultado admite hasta 128 referencias, 4 MiB por archivo referenciado y 32 MiB acumulados contando lecturas repetidas. La evidencia de líneas usa UTF-8. El CLI usa los mismos bytes para validar SHA-256, localizador y formatos comunes de credenciales. Entrega artefactos previamente depurados. El control de texto cubre patrones comunes en el resultado y en referencias verificadas. El inventario de producto se verifica mediante huellas y queda fuera del análisis de contenido.

Las huellas y los IDs para deduplicar están separados por sesión. Si se agota la retención de detalles de auditoría, un resultado inválido de una sesión vinculada conserva su transición de reintento mediante un registro mínimo del despacho.

## Recuperación

El organizador guarda la reserva antes de lanzar la sesión. Si el proveedor devuelve cuota agotada, registra `pause DISPATCH_ID quota` con `--retry-at` ISO 8601 zonificado si está disponible. Para causas diferentes, usa `authentication`, `provider_failure` o `uncertain_dispatch`. La respuesta tipada debe provenir del controlador o proveedor.

Ejecuta `resume --capacity quota` si la cuota sigue agotada o `resume --capacity available` cuando vuelve. Un bloqueo distinto de cuota se conserva hasta reconciliarlo y registrar `resume --capacity reconciled`. El CLI conserva el mismo despacho e intento. Si el proceso se interrumpe antes del resultado, consulta primero el recibo y el estado de la sesión nativa. Continúa la sesión vinculada o entrega su resultado ya producido con el mismo `event_id`. Si no hay recibo y puedes establecer que el agente aún no se ejecutó, usa la reserva existente. Si el efecto previo es incierto, registra `uncertain_dispatch` y revisa el efecto antes de continuar. Para un ejecutor que pueda repetir despachos, exige deduplicación por `dispatch_id` o resultados aislados con promoción única a cargo del organizador.

Si la sesión vinculada dejó de estar disponible y su resultado no se puede recuperar, ejecuta `pause DISPATCH_ID uncertain_dispatch` sobre la reserva actual. El retorno de capacidad mantiene el caso en revisión. Si el organizador comprueba que la sesión anterior ya no puede producir resultados y que cualquier efecto observable quedó reconciliado, ejecuta `resume --capacity reconciled --retire-session SESSION_ID`, usando el recibo exacto. Después puede vincular un hilo nuevo al mismo despacho. El historial conserva ambos recibos y registra el retiro. Un resultado tardío de la sesión retirada y un intento de reutilizar ese recibo se rechazan. Si la reconciliación no es verificable, conserva la pausa.

El estado se reescribe atómicamente bajo exclusión y el historial conserva secuencia y huellas. El CLI recrea el handoff al reanudar si quedó atrasado. Una revisión obsoleta deriva al primer propietario afectado, conservando los registros históricos. Una rúbrica modificada o un estado incompatible detienen la operación para diagnóstico. El límite cuenta reservas principales y reintentos de evaluación rechazados. Una pausa mantiene intactos los contadores.

`status` revisa las huellas vigentes y persiste el rework correspondiente, incluso después de `COMPLETED`. El validador informa una revisión obsoleta sin escribir. Un resultado válido enviado durante una pausa puede reenviarse con el mismo `event_id` cuando se reanude el despacho. Si una huella cambia durante la pausa, el checkpoint conserva la reserva y registra el primer rol afectado. Un cambio de causa a `uncertain_dispatch` mantiene ese registro. La revisión del despacho debe terminar con `resume --capacity reconciled` antes de volver a abrir ese rol.

Una sola sesión del organizador ejecuta los comandos que pueden mutar el estado. Antes de cada mutación confirma en Codex el hilo nativo y el recibo correspondiente al resultado, o el evento de control que autoriza la operación. Los agentes solo devuelven resultados. El hash y el historial permiten detectar alteraciones accidentales o inconsistencias bajo esa frontera de confianza. Una persona con el mismo acceso de escritura puede editar el estado y regenerar sus huellas. Los perfiles de agentes heredan permisos del entorno. Si el gate de seguridad exige aislamiento verificable del plano de control frente a los subagentes, conserva el bloqueo hasta disponer de un entorno con identidades y permisos segregados.

En Windows, el lector comprueba rutas canónicas, enlaces y puntos de reanálisis, identidad del archivo abierto y cambios observables durante la lectura. El aislamiento frente a una sustitución intencional por un actor con los mismos permisos forma parte de la misma frontera de confianza.
